# IRB Watch: design interview record

Recorded 2026-11-04. Each entry is a question asked before planning, the answer given, and the reason. The approved plan is in `docs/plan.md`.

## Scope
- This repo is the **server only**. The frontend (Next.js) lives in a separate repo.
- Supabase (Postgres + Auth) is the database. The schema and migrations live **in this repo** under `supabase/migrations/`.
- The frontend reads data **directly from Supabase** (supabase-js + RLS). This server mostly writes, using the service-role key, and exposes few endpoints.

## Decisions

| Topic | Decision | Reason / note |
|---|---|---|
| Language | Python 3.11+, managed with uv | Better parsing libraries (PDF, HWP, OCR) than JS |
| Framework | FastAPI | Async, typed, auto OpenAPI docs |
| Agent role | Fixed pipeline. The OpenAI agent only summarizes diffs and ranks priority | Change detection must be deterministic and reproducible |
| Model control | `OPENAI_BASE_URL` + `OPENAI_MODEL` env vars, pointing at an OpenAI-compatible API gateway | User wants to switch models at the gateway. **Gateway not chosen yet** |
| URL source | Admin-managed global list. Users subscribe to items from it | Each URL is scanned once however many users follow it |
| Accounts | Created by admin only. Users log in with Supabase Auth afterwards | |
| Server auth | Verify Supabase JWT. Admin role gates admin endpoints (manage URLs, create users, trigger scans) | |
| Trigger | Built-in scheduler (APScheduler) plus an API endpoint | |
| Deploy | Single long-running container. A DB lock keeps later scaling safe | |
| Trackable unit | Linked files (PDF/HWP/DOCX) plus the page's own text | Catches notices as well as attachments |
| Storage | **Revised 2026-11-04:** store originals in a **private Supabase Storage bucket**, named by sha256. DB keeps the storage path (not a URL), hash, extracted text and the source post URL. Frontend gets short-lived signed URLs | Hospitals delete old versions; the site's download links are encrypted tokens, not permanent. Cloudflare R2 considered and deferred (negligible gain at this volume). Check hospital terms before sharing copies beyond internal users |
| Fetching | httpx by default. Playwright fallback per URL, set by a `needs_browser` flag | Keeps the image light unless JS rendering is needed |
| Login-only boards | **Added 2026-11-06.** A source with `config.login_user` logs in at the start of every scan with that user's stored ID/password (headless Playwright fills the site's own form, one attempt, cookies kept in memory only, then discarded). Credentials: Windows Credential Manager via `keyring`, key `<user>/snuh-<board_key>`, entered by the owner with `scripts/save_credentials.py`; never in the repo or read by the assistant. `scripts/save_login.py` (manual login, cookies in `data/sessions/`) is for exploring only | The site ends a session after 30 minutes idle, so a saved session cannot serve a daily scan. A wrong password is never retried (account lockout). Several sessions per account can coexist (tested live) |
| Login failures | `LoginRejectedError` (login refused, no stored credentials) and `LoginExpiredError` (login page where content was expected) set only that source to `needs_review` with the reason. A dead session mid-scan fails the scan; it is never recorded as one broken post per post | One site's login trouble must not stop other sources, and must not look like "no change" |
| Access to login-only content | **Applied 2026-11-06; read policies verified with six impersonated test users in a rolled-back transaction (follower without proof, valid proof, expired proof, proof without following, admin, public-only follower). Not yet tested: the endpoint with a real non-owner hospital account.** A source with `requires_login` is readable only by admins and by users who hold an unexpired proof in `source_access` (the "follow it" condition was dropped 2026-11-09, see "No subscriptions"). The proof is created by `POST /sources/{id}/access`: the user's OWN hospital ID/password are used once in memory (headless login, then one request for that board), never stored or logged; success = 30 days (`ACCESS_TTL_DAYS`), then the user logs in again. One rule, `private.can_read_source()`, backs the read policies of documents, versions, files and news cards, and the server's summary check mirrors it. Users stored copy is searched/read after proof; there is no live per-user search. `requires_login` is set when an admin gives a source a `login_user` and is never cleared automatically. Abuse guards, both counted from the audit log: 5 login checks per app user per hour (`ACCESS_ATTEMPTS_PER_HOUR`), and **3 failed logins per hospital ID per hour across all users** (`ACCESS_ID_FAILURES_PER_HOUR`), so several users cannot lock one hospital account together. The ID is logged only as `HMAC-SHA256(ACCESS_ID_HASH_KEY, trimmed lower-cased ID)` in the payload (`id_fp`) of `access.attempted/granted/denied`; the audit table never holds hospital IDs. A hospital ID's count = attempts minus granted minus denied-without-judging (`board_not_readable`, `check_failed`); an attempt with no logged result counts as a failure (safe direction). With no `ACCESS_ID_HASH_KEY` set, access checks answer 503 and try no login | Today any user can insert a subscription and read login-only data. A stored password is not proof of access; a successful login against that board is. Hospital access can be revoked, hence the expiry. Risk: our server briefly handles a user's hospital password; users must be told, and the endpoint must stay HTTPS-only |
| No subscriptions | **Decided 2026-11-09; migration `drop_subscription_requirement` written, NOT yet applied (waiting for the owner's go); offline tests only.** Admin and the scheduler scan; users only read. Every signed-in user may read every source (`private.can_read_source` = admin, or the source exists and is public, or the user holds an unexpired `source_access` proof). Scans keep using the admin's stored login; a user's own hospital login is still only a 30-day proof, used once in memory and never stored. `sources.is_active` is still ignored by the read rule (history of deactivated sources stays readable). `public.subscriptions` is kept with its audit trigger; `insert` is revoked from `authenticated`, so users cannot add rows; dropping the table is a later decision. Search over stored text stays out of scope | The only user-side choice was following a source, and every read rule required it; the owner wants a read-only user role. Consequence: news cards (`audit_logs`, category `document`) show to all users for readable sources, so the frontend can no longer filter a feed by subscription. The per-user caps on summaries (20/day) and download links (200/day) still bound cost and bulk copying |
| Atomic scan save | **Added 2026-11-06, applied and verified live the same day (a failing last insert rolled back documents, versions, files, cards and `last_scan_at`; grants: only `service_role` can execute; a normal rescan of source 6 succeeded):** one Postgres function `public.commit_scan()` saves documents, versions, files, news cards and the scan result (`last_scan_at`, status, lock release) in a single transaction; `service_role` only. The server sends the whole scan as one JSON call and refuses (source `needs_review`, "scan too large…") above `MAX_SCAN_PAYLOAD_BYTES` (default 20 MB; the largest real board is about 2 MB of text). Files in Storage are uploaded before and are not part of the transaction (hash-named, unused ones are harmless) | The first live scan of a login board failed mid-save and left 5 documents with no `last_scan_at`; a rerun would have treated the other posts as new. Cards were written after the data, so a failure there would lose them silently (next scan sees no change) |
| Server-side credential store | **Built and applied 2026-11-06. Verified live: grants (only `service_role`), a fake login round-tripped through the real table with the real key (stored value is ciphertext, a wrong key and a moved row are refused, cleaned up). Not yet exercised live: the admin API endpoints and a real scan using the database store.** `CREDENTIAL_STORE=keyring` (default, Windows Credential Manager, this PC) or `database`: table `site_credentials`, one row per `(owner_label, site)`, holding only Fernet ciphertext (`CREDENTIALS_KEY`, one key or several comma-separated for rotation, first encrypts). The plaintext repeats its own owner and site, so a ciphertext moved to another row is refused. Table: `service_role` only, no policies. A missing or wrong key, damaged data or an unreachable table raises `CredentialStoreError`: the source becomes `needs_review` with the reason and is **not** paused (nothing was sent to the hospital). Entering logins: **admin API** (owner's choice over a local script): `PUT/DELETE /admin/credentials/{owner}/{site}`, `GET /admin/credentials` (labels and dates only). The password is accepted once as a `SecretStr`, never returned or logged; each change is logged first, fail closed (`credentials.saved/deleted`). The API answers 409 unless `CREDENTIAL_STORE=database`. `scripts/migrate_credentials.py` copies a keyring login into the table, run by the owner | A server (Render) has no Windows Credential Manager. Risk accepted with the API route: hospital passwords pass through the web API over HTTPS (admin only, request bodies are not logged by the app); a local script would avoid that |
| File downloads | **Built 2026-11-06.** `POST /files/{file_id}/download-url` (`file_id` = `document_version_files.id`) returns JSON `{url, expires_at, filename}`: a Supabase Storage signed link valid **60 s** (`DOWNLOAD_LINK_TTL_SECONDS`) that sets the original filename. Any file of any stored version. Allowed for admins, and for followers (plus an unexpired proof of access for members-only sources) via the same read rule as the database policies. A file the user may not read answers 404 "file not found". A file with no stored original answers 404 with that reason. Non-admins: 200 links per day (`DOWNLOAD_LINKS_PER_DAY`, counted from the audit log). Every link is logged (`file.download_link`: user, file, sha256, version) **fail closed**: the log entry is written before the link is returned, and if it cannot be written the request fails with 503 and no link is delivered (the entry is also the daily-cap counter). The same applies to login checks (`access.attempted`: no entry, no hospital login). Other log writes stay best effort (`AuditSink.record`) while `record_required` is fail closed. Links also work for old versions of removed documents and for deactivated sources, because history is kept and the read rule ignores both. The daily cap has a small race under many simultaneous requests (count, then log); accepted since it only slows bulk copying | The bucket is private and has no policies on purpose, so only the server can hand out access; JSON (not a redirect) because a browser link cannot carry the login token. A short link limits damage from a copied URL; the log and cap slow bulk copying of members-only documents |
| Scheduler | **Built 2026-11-06. Pause-column migration applied; one live `run_all` over sources 4, 5 and 6 succeeded (3 x ok in 193 s, no changes found, so the change-card path was not exercised). The 06:00 trigger, startup catch-up, 1-hour retry and parallel sites are tested with fakes only. The scheduler is off until `SCHEDULER_ENABLED=true`.** APScheduler runs inside the API process. **Daily run 06:00 `Asia/Seoul`** (`SCAN_CRON`, `SCAN_TIMEZONE`). **Startup catch-up:** once, 15 s after start, for active sources whose last saved scan is older than 24 h (or never). **Parallelism:** one worker per site (host), sites in parallel, boards of one site one by one. **Overlap:** a source that is still scanning is skipped (the DB scan lock) and a `scan.skipped` entry records why; only one full run at a time (`scan.run_skipped`). **Retry:** a scan that failed only because the site was unavailable is retried once, 1 hour later (`scan.retry_planned`); any other failure waits for the next day. **Rejected login:** the source is paused (`sources.scans_paused_reason`) and every full run skips it; a person starting a scan of that source clears the pause only when that scan is saved (proof the login works); a new rejection replaces the reason; any other failure (site unavailable, crash, layout change) leaves the pause as it was, because the login was never checked. The runner re-reads each source just before scanning it, so a source paused or deactivated during a long run is skipped; a crashing planned retry is recorded as `scan.failed`. A 403/404/500 on the login form fails at once and is not retried later. **Manual:** `POST /admin/scans/run-all` uses the same runner and rules. Every full run ends with a `scan.run_finished` entry (counts) | Daily changes should be ready before the working day; an outage must neither skip a day nor pile up runs; a login failure or outage on one site must not stop another; and an automatic run must never retry a rejected password (account lockout). A paused or skipped source is always recorded, never silent |
| Temporary site errors | **Added 2026-11-06.** GET requests (pages, files, `robots.txt`) are retried on HTTP **502/503/504**, connection errors and timeouts: 3 tries, waits 5 s then 15 s (`FETCH_RETRY_WAITS_SECONDS`). Not retried: 500, 4xx (incl. 429), robots disallow, oversize, rejected logins. One scan may use at most **10 retries** in total (`FETCH_RETRY_BUDGET`); when they are used up the scan stops as `failed` with "site unavailable … stopped after N retries" and changes nothing. A single page that fails all 3 tries while budget remains is flagged as one broken post, as before. Login: loading the form is retried the same way; the submit is **never** retried, and a 5xx after submit or on the form is reported as "site unavailable", never as a wrong password | The hospital server returns intermittent 502s; one blip used to fail a whole scan, and a 502 on the login form looked like a rejected password. A site that is really down must produce one clear failure, not a card per post, and must not be hammered |
| First scan | Silent baseline, no "new" alerts | Avoids flooding users |
| Removals | Mark removed only after **2 consecutive misses** | A flaky page load must not look like mass deletion |
| Failures | Mark `needs_review` and keep the previous state. Never treat as "no change" or "deleted" | A failure that looks like "no updates" is the worst outcome |
| URL safety | Block private/internal IPs, http/https only, respect robots.txt | Admin-only URLs, but still guard against SSRF |
| Limits | Max file size, max docs per URL, per-domain delay, cap on LLM calls per run | Bounds OpenAI cost and load on hospital sites |
| Summary language | Same language as the source document | Avoids mistranslating regulatory wording |
| Notifications | Dashboard only for the MVP. No email | Email can be added later |
| Python version | Pinned to 3.12 (`>=3.12,<3.13`) | Libraries are best tested on 3.12; matches the Dockerfile. 3.14 worked but offered nothing here |
| Server layout | One FastAPI server plus Supabase. No separate BE service | A second service adds deployments, duplicate auth and failure modes. Extract later if needed |
| Schema tool | Supabase CLI SQL migrations, not SQLAlchemy/Alembic/Drizzle | Most schema work is RLS, triggers and Storage policies that Alembic cannot autogenerate |
| Profiles | `public.profiles(id uuid PK -> auth.users on delete cascade, email, display_name, role user/admin)`, created by an `auth.users` trigger | Role is never read from user-editable metadata. Users may update only `display_name` (column-level grant) |
| DB tables (MVP) | `profiles`, `sources`, `documents`, `document_versions`, `subscriptions`, `audit_logs` | Dropped `changes` and `scan_runs`: the feed comes from versions and the audit log; latest scan result lives on `sources` |
| Document model | One `documents` row per post; attachments are a JSON list inside each `document_versions` row | Avoids a files table. `change_type` is `baseline` (silent first scan) or `updated` |
| Audit log | Append-only `audit_logs`; categories document, scan, admin, user. No foreign keys, so entries outlive the rows they describe. Triggers log subscription and role changes | Feeds dashboard news cards. Users see document entries for subscribed sources; admins see all |
| Access model | Users read via supabase-js under RLS; all writes go through the server's service role; Storage objects readable only by the server, which issues signed URLs | Keeps the access checks in one place |
| JWT verification | Verify against the project's public ES256 key list; no JWT secret in `.env` | Confirmed from the project's JWKS endpoint |
| OpenAI endpoint | Empty `OPENAI_BASE_URL` means OpenAI direct; set means gateway. Gateway set without a model fails at startup; disable tracing in gateway mode | Model name is read from `.env`, never hardcoded |
| Sign-up | Public sign-up disabled (`enable_signup = false`) | Accounts are admin-created |
| Admin API scope (step 4) | Create user, list users, change role, soft delete, restore | Soft delete = `profiles.deleted_at` plus an auth ban; email stays reserved, restore undoes it |
| New user credentials | Admin sets a temporary password (min 8 chars); email auto-confirmed | No email service needed yet |
| Admin check | Role read from the database on every admin request | Demotions and deletions apply immediately; a stale token cannot keep admin rights |
| Lock-out guards | Refuse demoting or deleting yourself, and removing the last active admin | Count-then-write, so a simultaneous race is possible but unlikely at this scale |
| First admin | One-off script `irb_watch.scripts.create_first_admin`, reusable for the production project | Steps in `docs/runbook.md` |
| Role-change audit | Database trigger only, so role changes have no actor | User chose this over a server-written entry |
| Settings loading | `APP_ENV` selects `.env.<APP_ENV>`, default dev; real env vars override | Switching to production needs no code change |
| CORS | `FRONTEND_ORIGINS`, default `http://localhost:3000` | |
| Unreadable files | Two outcomes. **Hash-only** (expected, stable): scanned PDF, HWP/HWPX/DOCX with no extractor yet; tracked by file SHA-256, labelled "text not available", no alert on every scan. **Failure** (`needs_review`): corrupt, password-protected, over 500 pages, download error, or bytes that do not match a document extension (e.g. an HTML login page named .pdf) | A permanent, harmless "cannot read" must not look like a fault on every scan. Known limits: a hash changes on any byte difference, so a re-saved image PDF can look updated; hash-only files get no AI summary. OCR deferred |
| What counts as "updated" | A change in title, page text, or any attached file's bytes. A title-only change is an update with suggested priority `low`. If a file's bytes change but its extracted text does not (re-export), a silent `resaved` version is stored and no alert is raised | User decided title changes count. `resaved` stops a harmless re-save from alerting on every scan |
| Seeing what changed | Every version keeps its full page text and per-file extracted text. Changes are computed on demand between any two versions, chosen by version number or by date (`version_as_of`), as a word-level diff; `excerpt()` gives a compact view for cards and AI input | User wants users to see changes, with version and date control. Diffs over 20,000 words per side are not computed word by word |
| Change events | `new`, `updated`, `removed` (after 2 misses), `reappeared`. Failed posts go to `needs_review` and keep their old state; secret posts are neither seen nor missing; incomplete scans never count misses | Logic lives in `core/detect.py` against an in-memory store; the database layer comes later |
| Version history storage | Keep the full page text of every version and the extracted text of every file, forever. Files live in `document_version_files`; `document_versions.files` JSON was dropped | User chose completeness over storage savings so any two versions can be diffed. Revisit if the database grows large |
| Original files | Uploaded to the private bucket only when their SHA-256 is new; object name = hash; the database keeps the path | Unchanged files are never re-uploaded. Same file in many posts is stored once |
| Scan trigger | Manual first: `POST /admin/sources/{id}/scan` returns 202 and scans in the background; scheduler comes later | User chose this. The 404/409 checks happen before the 202 |
| Scan lock | `sources.scan_started_at` claimed atomically; a claim older than 30 minutes counts as a crashed scan | Two scans of one source must not overlap |
| Scan failure states | List-level layout change or incomplete list or robots block = source `needs_review`; network error or crash = `failed`. Neither changes any document. One broken post = that post `needs_review`, rest still processed | A failure must never look like "no change" or "deleted" |
| Baseline | `sources.last_scan_at` is set only by a scan that stored its results, so a failed first scan does not use up the silent baseline | Otherwise the next success would report every post as new |
| Title vs text | The title is removed from the stored page text before comparing | Otherwise a title edit would also count as a text edit |
| Adding a site | A new site needs an adapter, a reader and one branch in `api/deps.build_reader`, plus its name in the `sources.adapter` check constraint | Only `snuh_hrpp` exists today |
| Text formats | PDF, HWP 5.x, HWPX and DOCX are read; legacy `.doc` and HWP before 5.0 stay hash-only. HWP uses my own reader on `olefile` + `zlib` (BSD), not pyhwp (AGPL). DOCX keeps body, tables, headers, footers, footnotes, endnotes, text boxes and inserted tracked-change text; drops deleted text, comments and field codes | User chose all four formats and the DOCX scope. License reason for HWP. Readers parse XML with defusedxml and cap zip/deflate/text sizes; a file over a cap is refused, never cut short |
| Three outcomes for a file | **Hash-only (expected, no alert):** scanned PDF, HWP distribution document, unsupported type. **Unreadable (file-level):** real file we cannot read (corrupt, password-protected, too large, or a bug in a reader): post stays tracked, file tracked by hash, warning attached, document set to `needs_review`. **Post fails:** bytes are not the promised document (an HTML page named .pdf): post keeps its old state | Replaces the earlier rule that any parse error fails the whole post. User wants tracking to continue and the reason visible. An HTML error page must not be tracked as if it were the file |
| Failure visibility | `documents.review_reason` holds the reason; a `document.needs_review` audit entry (category `document`, so subscribers see it) is written when a post first needs review or its reason changes, not on every scan. Files keep `extract_note`. Reader bugs are logged with a traceback and shown as "internal error (ExceptionType)" | User: "users want to see why it fails". A post never stored before that fails again gets a notice each scan (no row to compare with) |
| AI pipeline | Jev (TypeSafe) classifies first, OpenAI writes the summary second. Jev answers three questions about the changes: priority (low/medium/high), "is it substantive" (yes/no probability, updates only) and document category. OpenAI is called through the plain **Responses API** (typed answer, `store=False`), not the Agents SDK or the managed Agents API | User chose the Responses API. The Agents API is a managed, asynchronous, sandbox-based, beta service with no zero-data-retention and no documented structured output: wrong shape for one short summary. The `openai-agents` dependency was removed. Jev cannot write text, so it only decides |
| What is sent out | Only the changes: title change, changed words with ~12 words of context, file names and (for new files) the start of their text, capped at 12,000 characters. New posts: title, start of text and files, capped at 12,000. A user-requested whole-document summary: up to 60,000 characters. Every cut is flagged and the summary says it may be incomplete. Document text is wrapped as untrusted data in the prompt | Smallest exposure and cost; prompt-injection hardening because scraped text is untrusted. Jev's docs state no input limit or retention |
| Skip rule | Title-only changes and changes Jev is confident are cosmetic (substantive probability below 0.15, priority low with confidence at least 0.6) get a plain template description in Korean or English (by the title's language), no OpenAI call. Unsure (confidence below 0.6): priority medium and a summary. A title-only change is always low whatever Jev says. The card is always written | User chose this. Thresholds are settings: `AI_SKIP_BELOW`, `AI_MIN_CONFIDENCE` |
| When it runs | During the scan, after change detection and before saving, so the version and its news card are written together (the audit log cannot be edited later). A failing service never fails the scan: Jev down = no priority or category; OpenAI down = template text for updates (deviation: the chosen rule said "no summary", a plain factual line is better), nothing for new posts. OpenAI calls per scan are capped by `MAX_LLM_CALLS_PER_RUN`; past it the template is used | |
| New posts | Summarized ("what it is and who it is for") and classified. The first-scan baseline produces no cards and no AI calls | User chose this |
| Categories and priority rubric | consent_form, application_form, sop, regulation_guideline, notice, reference, other; rubric in `irb_watch/ai/categories.py`. No database constraint on the values, so both can change later without a migration; old rows keep their old values | User: "may be changed later" |
| On-demand summary | `POST /documents/{id}/summary`: any signed-in, active user subscribed to the document's source (admins any). Summarizes the whole current document (page text plus readable attachments, up to 60,000 characters). Cached on the version; 20 newly generated summaries per user per day (`SUMMARY_REQUESTS_PER_DAY`); cached answers are free; a failed generation is neither saved nor counted. Documents the user may not see answer 404 | User chose these |
| Missing keys | No `OPENAI_API_KEY` or `OPENAI_MODEL`: AI summaries are off. No `TYPESAFE_API_KEY`: Jev is off. Scans and everything else keep working. No model name is hardcoded | Changes the earlier rule "gateway set without a model fails at startup": it now switches summaries off with a log warning |
| Tests touching Supabase | Offline tests by default; live test only with `RUN_LIVE=1` | User said the project is a test account, so the live test runs against it; it leaves append-only audit rows |
